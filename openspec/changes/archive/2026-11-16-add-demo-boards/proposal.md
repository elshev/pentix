## Why

The client can already auto-play a session with a pluggable demo engine (`delphi5`, `random`), but the player can only ever watch one session at a time and the space beside the board is deliberately empty. Running two small demo boards there — auto-played in parallel from the same piece sequence as the player's game — makes the engine differences visible at a glance, keeps the screen alive while no player game is active, and lays out the rail that will later hold twelve comparison boards.

## What Changes

- **A demo-board rail beside the main board.** The gameplay screen becomes two regions: the existing board-width column on the left, and a right-hand rail of small demo boards that starts at the top, its first row level with the main board's statistics line, and fills from its top-left corner. The rail is laid out as a `4`-column grid with room for `3` rows (twelve slots) so the planned 12-board wall needs no re-layout; this change fills only the first two slots.
- **Two small boards, two engines.** The second board is driven by the `Delphi 5` (`delphi5`) engine and the third by the `Random` (`random`) engine. Each small board shows its engine's display name so the two are distinguishable.
- **Small boards render at a reduced — but legible — scale.** A new `--demo-cell-size` variable sizes their minos at `9px` by default, `7px` at a `1000px` viewport and `6px` at the `900px` breakpoint, with a slightly wider slot gap so neighbouring boards stay distinct; the boards keep the shared board's stored `width`-by-`height` grid and the same cell coloring and active-piece overlay as the main board.
- **Only the main statistics on a small board.** Each small board shows `Score`, `Lines`, and `Pieces` read from its own session plus its engine name. It has no next-piece preview, no pieces statistics popup, no level selector, no action counters, no on-screen controls, and no overlays.
- **A board set starts in parallel.** Starting a player game on the main board (`Start`, `Restart`, a level pick on the game-over screen) creates a fresh session on the main board **and** on each small board from the **same `PentixGame`**, so every board draws the same piece at the same sequence index. The initial attract demo on page load also starts the full set.
- **The piece sequence is shared, the sessions are not.** The reducer keeps one `game` (piece list) and each board keeps its own board snapshot, statistics, level progression, and piece index. Extending the sequence on one board extends it for all of them, so two boards at the same `nextPieceIndex` always hold the same piece.
- **Small boards keep running when the main board stops.** When the main board reaches game over, pauses, or runs its attract demo, the small boards continue on their own timers. A small board whose own session ends holds its final board and shows a game-over marker until a new main session starts.
- **The attract demo's automatic restart does not reset the small boards.** `demoRestart` (the `700` ms restart of the main attract demo) leaves the small-board sessions untouched, so they are not wiped every few seconds. Only a new session started by the player (or the initial page-load set) resets them.
- **Per-board auto-play through the shared engine.** Each small board runs the existing demo step — one gravity descent plus one steering step per interval at its own session level — planned with its own engine and cached per piece, through `GameSessionEngine`; nothing about gravity, movement, locking, or game over is re-implemented. `Random` therefore never side-steps and `Delphi 5` may side-step on the last tick.
- **The pieces statistics popup keeps affecting only the main board.** Opening it pauses the player game / main attract demo, as today, and the small boards keep advancing.
- **The demo level controls retune the whole rail.** While the main board runs its attract demo (including the post-game-over delay), choosing a level with the level buttons, `+`/`-`, or a `0`-`9` key applies it to the main demo session and to every small board, so all boards play at the same speed. During a player game a level change still affects only the player's session.
- **Narrow viewports stack the rail.** At mobile widths the rail moves below the main column so the board is never squeezed.
- **BREAKING (state shape only):** the reducer state gains a `demoBoards` collection and the demo step gains a board identifier. Nothing outside `apps/pentix-web` consumes the reducer state, and `packages/pentix-core` / the REST contract are unchanged.

## Capabilities

### New Capabilities

- `demo-boards`: the parallel small demo boards — their board set (one shared `PentixGame`, one session per board), the fixed engine assignment (`delphi5` on the second board, `random` on the third), their auto-play loop, their reduced rendering with primary statistics only, and their lifecycle relative to the main board (start in parallel, keep running after main game over, hold the final board, reset only on a new main session).

### Modified Capabilities

- `browser-gameplay`: the "single column with nothing beside the board" requirement is replaced by a two-region gameplay layout (board-width main column plus a bottom-right demo boards rail reserving a `4 × 3` grid); the shared-board rendering requirement gains the reduced demo-board mino size; the statistics and controls requirements are restated so they apply to the main board only.
- `repository-documentation`: the capabilities-as-built list gains the two parallel demo boards and their engines, so the root documentation keeps matching the shipped client.

## Impact

- **Affected code**: `apps/pentix-web/src/engine/gameReducer.ts` (demo-board state, board-set creation, shared `game` merging, the `demoBoardStep` action, and a `demoRestart` that keeps the boards), `apps/pentix-web/src/engine/demo.ts` (steering helpers reusable per engine and board), `apps/pentix-web/src/games/pentix/Game.tsx` (two-region layout plus the rail), new `apps/pentix-web/src/games/pentix/DemoBoard.tsx` and `apps/pentix-web/src/games/pentix/useDemoBoard.ts` (small-board rendering and per-board stepper), `apps/pentix-web/src/games/pentix/BoardView.tsx` (compact variant), `apps/pentix-web/src/games/pentix/useDemoController.ts` (shared stepper used by the main and the small boards), and `apps/pentix-web/src/App.css` (`--demo-cell-size`, the layout grid, the rail, and the small-board styles).
- **Unaffected**: `packages/pentix-core` (both demo engines and the registry are already exported), `apps/pentix-server`, the REST contract, `GameSessionStatistics`, and the keyboard bindings (they still drive the main board only). No new dependencies.
- **Documentation**: `README.md` gains the two demo boards in its browser-client capability list, so the root documentation keeps matching the shipped client.
- **Tests**: `tests/pentix-web.test.mjs` gains reducer coverage for the board set (two boards, engine ids, distinct sessions, one shared `game`), the lifecycle (start/restart/level-pick reset, `demoRestart` does not, main game over does not), per-board stepping (only the addressed board advances, stale steps are ignored, a finished board ignores steps), and the shared piece sequence. Verification is `npm run lint`, `npm run build:web`, `npm test`, plus a visual check at desktop, `900px`, and mobile widths.
- **Affected teams**: the frontend/game-UI stream only. Shared-core and server owners are unaffected — no engine or API contract changes.
- **Rollback plan**: revert the touched `apps/pentix-web` files and `tests/pentix-web.test.mjs`, delete `DemoBoard.tsx` and `useDemoBoard.ts`, and restore the single-column layout, to return to one board with the attract demo and an empty area to its right. There is no data migration and no persisted state — the board set lives only in reducer memory — so rollback is isolated to the web app and cannot affect the core package, the server, or stored sessions.
